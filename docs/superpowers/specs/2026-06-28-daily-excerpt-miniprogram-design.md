# 每日精美文摘微信小程序 MVP 设计

## 1. 目标

第一版做一个极简微信小程序，用于验证“用户每天打开后阅读一篇精美文摘，并能回看历史文摘”的核心体验。

系统每天自动从固定公开来源采集内容，整理成当日短文摘，发布到微信云数据库。小程序端只负责展示今日文摘和历史记录，不做后台管理、登录、收藏、评论、点赞或复杂推荐。

## 2. 范围

### 2.1 第一版包含

- 微信小程序首页展示今日文摘。
- 历史页按日期倒序展示往期文摘。
- 详情页展示某一天的完整文摘。
- GitHub Actions 每日定时运行自动更新任务。
- 固定少数公开来源账号作为素材源。
- HTML 正文提取。
- 云 OCR API 识别图片文字，用于辅助段落纠正。
- 规则清洗与分段，第一版不强依赖大模型。
- 微信云数据库保存文摘、素材来源和任务日志。
- 抓取失败或无新内容时，从素材库候选池补发一篇。
- GitHub Actions 日志保留详细技术错误，云数据库 `job_logs` 保留结构化运行记录。

### 2.2 第一版不包含

- 后台管理页面。
- 用户登录或个人中心。
- 收藏、点赞、评论、分享卡片。
- 关键词全网搜索采集。
- 高频抓取、并发抓取或绕过登录、验证码、风控。
- 大模型改写、摘要、创作或自动生成新文摘。
- App Store / Android 原生 App。

## 3. 用户体验

### 3.1 首页

首页打开即展示最新已发布文摘。

显示内容：

- 日期。
- 标题。
- 来源名称。
- 分段正文。

如果当天任务失败但补发成功，用户端仍看到一篇正常文摘，不显示技术错误。

### 3.2 历史页

历史页按日期倒序展示文摘列表。

每条列表项显示：

- 日期。
- 标题。
- 来源名称。
- 正文摘要。

点击列表项进入详情页。

### 3.3 详情页

详情页展示选中文摘的完整内容，布局与首页保持一致。

## 4. 系统架构

```text
固定公开来源
→ GitHub Actions 定时任务
→ Python 采集与解析脚本
→ HTML 正文提取
→ 图片 OCR
→ 规则清洗与分段
→ 今日文摘
→ 写入微信云数据库
→ 微信小程序读取展示
```

失败兜底流程：

```text
抓取失败或没有新内容
→ 从素材库候选池选择一篇未发布素材
→ 发布为今日文摘
→ 写入 job_logs，记录 fallback_used 和原因
```

## 5. 组件

### 5.1 微信小程序

职责：

- 读取最新已发布文摘。
- 读取历史文摘列表。
- 展示文摘详情。

小程序不直接抓取网页，也不直接调用 OCR API。所有采集、清洗、发布逻辑都在自动任务侧完成。

### 5.2 GitHub Actions

职责：

- 每天定时触发更新任务。
- 执行 Python 脚本。
- 记录详细运行日志。
- 将生成的文摘和任务状态写入微信云数据库。

GitHub Actions 需要保存以下密钥：

- 微信云开发访问凭据。
- OCR API 凭据。

### 5.3 Python 自动更新脚本

职责：

- 读取固定来源配置。
- 抓取公开页面。
- 缓存原始 HTML 和图片识别结果。
- 提取标题、正文、图片和来源信息。
- 调用云 OCR API 识别图片文字。
- 使用规则清洗正文并修正分段。
- 去重，避免重复发布同一篇内容。
- 写入微信云数据库。
- 写入任务日志。

### 5.4 微信云数据库

职责：

- 保存已发布文摘。
- 保存固定来源配置。
- 保存候选素材池。
- 保存每日任务日志。

## 6. 数据模型

### 6.1 `excerpts`

每日文摘集合。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 文摘 ID |
| `date` | string | 发布日期，格式 `YYYY-MM-DD` |
| `title` | string | 文摘标题 |
| `paragraphs` | string[] | 分段正文 |
| `summary` | string | 列表摘要 |
| `source_name` | string | 来源名称 |
| `source_url` | string | 来源链接 |
| `source_account_id` | string | 来源账号或页面 ID |
| `content_hash` | string | 去重哈希 |
| `publish_type` | string | `fresh` 或 `fallback` |
| `status` | string | `published` |
| `created_at` | datetime | 创建时间 |

### 6.2 `sources`

固定采集来源集合。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 来源 ID |
| `name` | string | 来源名称 |
| `platform` | string | 来源平台，例如 `xiaohongshu` |
| `profile_url` | string | 公开主页 URL |
| `enabled` | boolean | 是否启用 |
| `last_checked_at` | datetime | 最近检查时间 |
| `created_at` | datetime | 创建时间 |

### 6.3 `material_pool`

候选素材池集合，用于失败补发。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 素材 ID |
| `title` | string | 标题 |
| `paragraphs` | string[] | 已清洗正文 |
| `summary` | string | 摘要 |
| `source_name` | string | 来源名称 |
| `source_url` | string | 来源链接 |
| `content_hash` | string | 去重哈希 |
| `status` | string | `candidate`、`used` 或 `discarded` |
| `created_at` | datetime | 创建时间 |
| `used_at` | datetime | 使用时间，可为空 |

### 6.4 `job_logs`

每日任务日志集合。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 日志 ID |
| `date` | string | 任务日期，格式 `YYYY-MM-DD` |
| `status` | string | `success`、`fallback_used` 或 `failed` |
| `source_name` | string | 本次尝试来源 |
| `excerpt_id` | string | 发布文摘 ID，可为空 |
| `fallback_material_id` | string | 补发素材 ID，可为空 |
| `message` | string | 简短说明 |
| `error_detail` | string | 错误详情，可为空 |
| `created_at` | datetime | 创建时间 |

## 7. 内容处理规则

### 7.1 输入

- HTML 提取正文。
- 图片 OCR 文字。
- 标题。
- 来源名称和链接。

### 7.2 清洗

规则清洗第一版承担主要处理职责：

- 去除多余空白。
- 去除平台通用文案。
- 去除明显无关的标签或引导语。
- 按中文标点切句。
- 合并过短句。
- 拆分过长段。
- 使用 OCR 结果中的换行和文字块顺序辅助判断段落边界。

### 7.3 输出

第一版输出短文摘，正文以 2 到 5 段为目标。系统尽量保留原文表达，不主动扩写、摘要或改写观点。

### 7.4 大模型边界

第一版不强依赖大模型。后续可以在规则置信度低、OCR 质量差或需要摘要改写时引入大模型作为增强能力。

## 8. 错误处理

### 8.1 抓取失败

如果公开页面无法访问、返回登录/验证码/风控页面，任务停止继续抓取该来源，不绕过限制。

处理方式：

- 从 `material_pool` 选择一篇可用候选素材补发。
- 写入 `job_logs.status = fallback_used`。
- 在 `message` 和 `error_detail` 中记录原因。

### 8.2 OCR 失败

如果 OCR API 失败：

- 优先使用 HTML 正文进行规则分段。
- 如果 HTML 正文可用，仍可发布。
- 如果 HTML 正文也不可用，则进入补发流程。

### 8.3 无新内容

如果固定来源没有新内容：

- 从素材库候选池补发。
- 写入 `job_logs.status = fallback_used`，原因记录为 `no_new_content`。

### 8.4 无候选素材

如果抓取失败且候选池为空：

- 当天不发布新文摘。
- 小程序首页展示最近一篇已发布文摘。
- 写入 `job_logs.status = failed`。

## 9. 合规边界

第一版只处理公开可访问内容，不绕过登录、验证码、风控或私密内容限制。

采集内容用于内部素材整理和每日文摘展示验证。文摘记录保留来源名称和来源链接。后续如果产品正式对外推广，需要进一步明确版权策略、授权来源、引用比例、改写策略和内容审核流程。

## 10. 测试策略

### 10.1 脚本测试

- 使用现有原始 HTML 快照作为 fixture。
- 测试单篇笔记解析。
- 测试用户主页解析。
- 测试正文清洗与分段。
- 测试 OCR 结果参与分段的规则。
- 测试抓取失败时补发素材。
- 测试重复内容不会重复发布。

### 10.2 小程序测试

- 首页能展示最新文摘。
- 历史页按日期倒序展示。
- 详情页能展示完整分段正文。
- 无当天文摘时展示最近一篇已发布文摘。
- 空历史状态有明确但克制的提示。

### 10.3 自动任务测试

- GitHub Actions 可手动触发。
- 成功任务写入 `excerpts` 和 `job_logs`。
- 失败任务写入 `job_logs`。
- OCR 失败时按预期降级。

## 11. 实施顺序

1. 固化项目结构、README 和依赖说明。
2. 建立清洗分段模块和 fixture 测试。
3. 增加素材池和失败补发逻辑。
4. 增加 OCR API 接入与缓存。
5. 接入微信云数据库写入。
6. 配置 GitHub Actions 定时任务。
7. 创建极简微信小程序页面：首页、历史页、详情页。
8. 小程序接入微信云数据库读取。
9. 做一次端到端 dry run。
